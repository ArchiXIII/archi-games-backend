# Archi Games Backend

Production-oriented serverless backend для HTML5-игр Archi Games. Первая конфигурация — `crystal-match` на VK. Runtime: Node.js 22, CommonJS, Yandex Cloud Functions, API Gateway и YDB Serverless.

## Архитектура

`index.js` создаёт зависимости один раз на холодном старте. Лёгкий роутер адаптирует событие API Gateway, ограничивает JSON, применяет CORS, проверяет VK launch params и формирует единые ответы. Сервисы не зависят от транспорта. Репозитории инкапсулируют YQL и официальный YDB SDK. Драйвер и пул сессий переиспользуются между вызовами.

Выдача покупки принимает только `productId`; количество монет берётся из серверного каталога. Создание заказа, создание игрока и увеличение баланса выполняются одним сериализуемым запросом. Первичный ключ заказа обеспечивает идемпотентность.

## Требования

- Node.js 22 и npm
- YDB Serverless
- сервисный аккаунт функции с `ydb.editor`
- сервисный аккаунт API Gateway с правом вызова функции

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `YDB_ENDPOINT` | `grpcs://ydb.serverless.yandexcloud.net:2135` |
| `YDB_DATABASE` | полный database path |
| `VK_APP_ID` | ID приложения VK |
| `VK_APP_SECRET` | защищённый ключ приложения для проверки launch params |
| `VK_CALLBACK_SECRET` | секрет/ключ callback после подтверждения протокола VK |
| `ALLOWED_ORIGINS` | список origin через запятую |
| `NODE_ENV` | `production` |

Секреты задаются только в окружении функции. JSON-ключ сервисного аккаунта не нужен и не должен создаваться: в Cloud Function SDK получает IAM-токен через metadata service.

## Тесты

Установить зависимости и выполнить:

`npm ci`

`npm test`

Тесты используют встроенный `node:test` и не требуют YDB.

## Миграции

Миграции не запускаются HTTP-handler и безопасны при повторном выполнении.

Локальный запуск с доступом к metadata service:

`npm run migrate`

Для запуска с рабочей станции предпочтительно применить `migrations/001_initial_schema.sql` через Query Editor в консоли YDB. Не создавайте постоянный JSON-ключ. Если миграция временно запускается как Cloud Function, используйте отдельную версию/entrypoint-обёртку, тот же сервисный аккаунт и удалите обёртку после выполнения.

## Сборка ZIP

`npm run build:zip`

Команда создаёт чистый staging-каталог, устанавливает только production dependencies и формирует `dist/archi-games-api.zip`. `index.js` и `package.json` находятся в корне архива.

## Развёртывание Cloud Function

В веб-консоли Yandex Cloud откройте `archi-games-api`, создайте новую версию и загрузите `dist/archi-games-api.zip`:

- runtime: Node.js 22
- entrypoint: `index.handler`
- memory: 256 MB
- timeout: 5 секунд
- service account: `archi-games-backend-sa`
- переменные окружения: из таблицы выше

Проверьте, что у аккаунта функции есть `ydb.editor`, а JSON-ключи и секреты не добавлены в ZIP.

## API Gateway

В `openapi.yaml` замените `${APIGATEWAY_SERVICE_ACCOUNT_ID}` на ID сервисного аккаунта, который API Gateway использует для вызова функции. В веб-консоли откройте `archi-games-gateway`, обновите спецификацию и сохраните. Не подставляйте имя аккаунта вместо ID.

Проверка:

`curl https://d5dl7q0eh16ojp505u1v.6brbn2wz.apigw.yandexcloud.net/health`

## Подключение Crystal Match

Клиент передаёт исходную строку VK launch params в `X-VK-Launch-Params` либо `Authorization: VK <params>`. Сервер проверяет HMAC и получает `vk_user_id` только из подписанных параметров.

- `GET /v1/player/balance` возвращает серверный баланс.
- `POST /v1/player/sync` принимает JSON только с `settings` и `progress`; монеты и платные ресурсы отклоняются.
- клиент не подтверждает покупку и не передаёт количество монет.

Текущая схема YDB не содержит колонок прогресса, поэтому безопасные поля sync валидируются и отражаются в ответе, но пока не сохраняются.

## VK Payments callback

Endpoint и сервисные интерфейсы подготовлены, но callback намеренно отвечает `501 VK_CALLBACK_NOT_CONFIGURED`. Формат нельзя выдумывать. Перед включением необходимо получить из актуальной документации и кабинета VK:

- точные типы callback для информации о товаре, успешной покупке и возврата;
- способ и поля проверки подлинности server-to-server запроса;
- точные имена полей order ID, user ID, product ID, status и currency;
- алгоритм успешного и ошибочного ответа VK;
- правила повторов, таймауты и переходы статусов;
- production callback secret/key и разрешённые настройки приложения.

Ответ VK Bridge на клиенте не считается подтверждением оплаты. После реализации адаптер должен преобразовать проверенный callback во внутреннюю команду `PurchaseService.grant`.

## Повторные callback и восстановление

Повторный callback с тем же `(platform, platform_order_id)` возвращает уже достигнутый результат и не увеличивает баланс. Обработку заказа и баланса нельзя разделять между транзакциями.

При неопределённом результате запроса VK должен повторить тот же callback с тем же order ID. Оператор проверяет строку `orders`, баланс `players` и события `purchase_events`. Не создавайте новый order ID для повторной выдачи. Для ручной компенсации нужен отдельный аудируемый административный процесс; прямое редактирование баланса не предусмотрено.

## Добавление второй игры

Добавьте каталог в `PRODUCTS`, разрешённый `gameId`, конфигурацию платформы и её проверяемый auth/callback-адаптер. Ключи YDB уже включают `game_id` и `platform`. Не смешивайте секреты и callback-контракты разных приложений.

## Безопасность

- HMAC сравнивается через `crypto.timingSafeEqual`.
- CORS выдаётся только allowlist origin и не является защитой callback.
- размер тела ограничен 64 KiB, JSON и `Content-Type` проверяются.
- клиентские ошибки не раскрывают внутренние сведения.
- логи содержат request ID, но не launch params, токены и подписи.
- секреты и service-account JSON исключены из репозитория и архива.
- каталог товаров и количество монет принадлежат серверу.
